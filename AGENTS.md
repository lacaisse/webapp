# Project conventions

This is an admin dashboard. Follow industry best practices for a Next.js admin app and the rules below.

## Data access
- All database calls and any external service calls that don't require the client to make them itself go through **server actions**. This keeps secrets and trust on the server.
- Database queries live in a dedicated **service folder** (e.g. `app/services/db/`) and are only imported by server actions — never by components or client code.
- External services (auth, email, payments, etc.) get their own service module under the same pattern, so they're easy to swap.

## Routing & state
- Route by **path and query parameters** so browser back/forward and shareable URLs just work. Do not stash navigation state in client-only state when a URL param would do.
- Load initial page data **server-side** wherever possible. Use `<Suspense>` boundaries with **skeleton fallbacks** for maximum perceived responsiveness.

## Mutations & UX
- For UI-affecting mutations, prioritise responsiveness: be **optimistic** (e.g. `useOptimistic`) and reconcile with the server response.
- **Never use `alert()`/`confirm()`/`prompt()`.** Use in-app modal/toast components for messaging and confirmation.
- **Always confirm destructive actions** (delete, archive, irreversible changes) with an in-app confirmation step before firing the server action.

## Stack
- **Auth**: **Better Auth** (`better-auth` + `@better-auth/passkey`), self-hosted on our Postgres via the Prisma adapter. Centralized login on `auth.<APP_DOMAIN>` with a cross-host session handoff (see the Auth sections below).
- **Database**: Postgres on Supabase, accessed via **Prisma**. Supabase is only the database host — the Supabase JS client is not used anywhere (auth is Better Auth, queries are Prisma).
- **UI**: shadcn/ui — `style: "base-nova"`, neutral base, `iconLibrary: "lucide"`. ⚠️ The `base-nova` variant is built on **`@base-ui/react` (v1.3)**, **not Radix** — when adding components or reading docs, use Base UI primitives. Utilities: `lucide-react`, `class-variance-authority`, `clsx`, `tailwind-merge`, `tw-animate-css`.
- **Forms**: `react-hook-form` + `zod` (schemas shared between client validation and server action input parsing).
- **Hosting & cron**: Vercel (production). The same code also builds as a container for Citizen Pay's self-hosted platform (staging first): `Dockerfile`, opt-in `NEXT_OUTPUT=standalone`, release command `node release/release.mjs [--seed]`, `/api/health` + `/api/health/ready`, the runner calling the crons with the same bearer. Everything about it is in `docs/container.md`; nothing there changes the Vercel build. The image sets `DEPLOY_TARGET=container`, which makes `services/cron/guard.ts` treat it as production (bearer mandatory).
- **Open Banking & blockchain**: **Citizenpay** (custom integration — details TBD).

## Framework gotchas worth remembering

These are non-obvious facts about the Next 16 / Prisma 7 stack that bit us during scaffolding.

### Next 16
- **`middleware.ts` is now `proxy.ts`**, function `proxy()`. Same `NextRequest`/`NextResponse` API. Runs on Node.js runtime (needed for the Prisma fund lookup). See `proxy.ts` at the project root.
- **`cookies()` is async** — always `await cookies()`. Same for `headers()`.
- Use **`refresh()` from `next/cache`** for client-router refresh after a Server Action — but it is **server-action-only**: calling it from a Client Component throws `refresh is only available in a Server Component` at runtime. Put it inside the action, or use `useRouter().refresh()` when the refresh must happen client-side (e.g. only on certain results, or mid-loop).

### Prisma 7
- **`PrismaClient` requires a Driver Adapter** (or Prisma Accelerate URL). The old "just pass DATABASE_URL" path is gone. We use `@prisma/adapter-pg` — see `services/db/prisma.ts`.
- **The new `prisma-client` generator emits ESM TypeScript source files**, not compiled JS. Output is configured to `services/db/generated/` (gitignored). Import the client from `services/db/generated/client`, **not** `@prisma/client`. The `@prisma/client` package is still a peer dep but no longer the import surface for `PrismaClient`.
- **`prisma.config.ts`** replaces CLI flags / `package.json` config. The datasource URL there is what Prisma CLI uses for `migrate`, `db push`, `studio`. Runtime PrismaClient picks its own URL via the adapter — that's how we split DIRECT_URL (CLI/migrations) from DATABASE_URL (pooled, runtime).
- **Database TLS (self-hosted only)**: `DATABASE_CA_CERT` (a PEM) makes every connection TLS verified against that CA (`services/db/tls.ts::pgTlsConfig` for the app, the seed and the rotation script; `docker/release.mjs` writes it to a temporary file for the migration engine, which takes `sslcert=<file>&sslaccept=strict`). Unset = the URL is used as is (Vercel). Any new script that opens its own `PrismaPg` should go through `pgTlsConfig`.
- `.env` is **no longer auto-loaded** — `prisma.config.ts` does `import "dotenv/config"` to load it.
- **Supavisor pooler compatibility**: `@prisma/adapter-pg` disables prepared statement caching by default, so `DATABASE_URL` can point at Supabase's transaction-mode pooler (port 6543) without extra config.

### Auth (Better Auth + DAL)
- **Better Auth replaced Supabase Auth.** The server instance lives in `services/auth/better-auth.ts`: Prisma adapter on our own Postgres, email+password enabled, passkey plugin, and `nextCookies()` **last** in the plugin list (it auto-writes cookies on Server Action responses). Signing secret comes from `BETTER_AUTH_SECRET`; `baseURL` is the auth host (`auth.<APP_DOMAIN>`).
- **Better Auth owns the `User` table directly**, plus `Session`, `Account`, `Verification`, and `Passkey` — the schema shapes are dictated by the adapter/plugins, don't rename fields or change types. Ids are Postgres-side `gen_random_uuid()` (via `advanced.database.generateId: "uuid"` + `@default(dbgenerated(...))`).
- The DAL (`services/auth/dal.ts`) wraps `getCurrentUser`, `requireUser`, `requireAdmin` in React's `cache()`; `requireFundRole(minRole)` composes them. `getCurrentUser` calls `auth.api.getSession({ headers })` then fetches the full Prisma `User` (the session's user shape lacks `globalRole` and relations).
- Sessions are **DB-backed and looked up on demand** — `proxy.ts` does no session work at all (nothing to refresh, unlike the old Supabase token dance).
- `requireUser` redirects anonymous users via `loginUrlForCurrentRequest()` (private helper in `dal.ts`): on the auth host it's a local `/login`; on apex/fund hosts it's `getAuthUrl("/login?return_to=<absolute current URL>")`, rebuilt from the `x-pathname` / `x-search` headers that proxy.ts forwards.
- The catch-all handler `app/api/auth/[...all]/route.ts` mounts Better Auth on **every** host. Server actions call `auth.api.*` directly (no Origin header → Better Auth's CSRF origin check is skipped); browser-driven flows (the passkey ceremony) POST to `/api/auth/*` on the current origin and **are** checked — `trustedOrigins` in `better-auth.ts` lists the apex + `*.<APP_DOMAIN>` and dynamically trusts paid custom domains via the proxy-validated `x-fund-domain` header. An "Invalid origin" error means a host class is missing there.
- Client side: `services/auth/client.ts` exports `authClient` (`createAuthClient` + `passkeyClient`), `baseURL` omitted so requests target the current origin's `/api/auth`. Use `signIn`, `signUp`, `signOut`, `passkey`, `useSession` from `"use client"` components. Login/signup/reset forms live in `app/(auth-host)/` and their server actions in `app/(auth-host)/actions.ts`.

### Auth hosts & cross-host session handoff
- Login UI lives on a dedicated **auth host** `auth.<APP_DOMAIN>` (route group `app/(auth-host)/`). `proxy.ts` classifies every request as `auth` | `apex` | `fund` and forwards `x-host-type`; read it via `services/host/server.ts` (`getHostType`, `getAuthUrl`). **Never re-parse the Host header.**
- **Each host owns its own session cookie** — host-only (no `Domain` attribute), no `crossSubDomainCookies`. That's deliberate: it survives third-party-cookie blocking and spans paid custom domains, which cookie-sharing can't.
- **Google-style handoff**: after authenticating on the auth host, actions call `buildPostAuthRedirect` (`services/auth/redirects.ts`). It validates `return_to` (apex or a registered `Fund.domain`; the auth host is never a valid target), mints a single-use 30s `AuthExchange` code bound to (userId, targetHost) (`services/auth/exchange.ts`), and redirects the browser to `<target>/auth/exchange?code=…`. Never `redirect()` straight to a non-auth origin after signing someone in — always go through this helper.
- The target host's `app/auth/exchange/route.ts` consumes the code (atomic `updateMany`, host-bound so a code minted for fundA can't replay on fundB), mints a fresh session via `auth.$context.internalAdapter.createSession`, and writes the signed cookie **on the redirect response itself** — cookies staged via `cookies()` don't survive into a freshly constructed `NextResponse`. It also HMAC-signs the cookie value itself and must NOT pre-URL-encode it (see comments in the route).
- Logout (`app/auth/logout/route.ts`) invalidates **all** the user's session rows, not just the local one — every other host's stale cookie then fails its DB lookup on next use. Expired `AuthExchange` rows are swept by `app/api/cron/auth-exchange-cleanup`.
- There is no sign-up of its own: Better Auth's public `/api/auth/sign-up/email` is disabled (`emailAndPassword.disableSignUp`), and `signupAction` creates an account only through `services/auth/signup.ts::createInvitedAccount` — the `returnTo` must be a `/join-team?token=…` URL whose live `FundInvite` is for exactly that email (the token reached the inbox, so the account starts `emailVerified`). It then signs the new account in with `auth.api.signInEmail` and hands it over through the exchange like a login. Two more doors write the same two rows (`User` + credential `Account`) through Prisma, inside their own transaction: the member login (below) and the apex `/join`, "Start your fund", where anyone creates an account and a fund together (see "Fund setup checklist & subscription"). The waitlist (`services/waitlist`, `WaitlistEntry`) only records interest and is no longer offered anywhere: the landing's get-started section, the hero's fallback link, the login footer and the auth host's `/signup` all lead to `/join`.
- Invite acceptance (`acceptFundInviteAction`) refuses an unverified account created before the invite was sent (`services/fund-team/invite-rules.ts` — a pre-registered account is the "pre-hijack" case) and marks the accepting account's email verified. A password reset revokes every session (`revokeSessionsOnPasswordReset`) and, for an account nobody had verified, drops its passkeys and marks the email verified (`onPasswordReset`): the reset link is the recovery path.
- **Safe (multisig) guardrails** (`services/safe/*`, security review 2026-10-29): signer keys are sealed with GCM additional data `signer:<fundId>:<userId>` (envelope `v2`, `services/crypto/secret.ts`; legacy `v1` rows re-seal on next signature) so a ciphertext copied onto another row cannot sign. Sync reads the Safe's singleton / guard / modules / fallback handler (`relayer.ts::readSafeConfig`) and stores any drift on `FundSafe.configWarning`; `tryExecute` refuses (`reason: "config"`) while it is set. Proposals take the lowest free nonce ≥ the chain nonce, are capped (`MAX_OPEN_PROPOSALS_PER_SAFE` / `_PER_PROPOSER`, rejections exempt) and can be withdrawn by the proposer or a fund OWNER (`withdrawProposal`, deletes the row; a mirrored one stays visible in Safe{Wallet}). Rename / archive / unarchive need a current owner or a fund OWNER; archive is refused with open transactions or while a team-dependent Safe holds value (`holdings.ts`). Team actions refuse to demote or remove a member whose signer a Safe needs (`guardrails.ts`). The relayer caps gas per execution (`EXEC_GAS_CAP`) and persists the broadcast hash before waiting for the receipt (`onBroadcast`). Error text stored on rows goes through `redact.ts` (RPC key). Addresses in Safe inputs and custom-token registration are strict EIP-55; custom-token symbols may not collide with the fund token or built-ins (`services/token/symbol.ts`).
- **Passkey-backed Safe owners** (`docs/safe-passkeys.md`): a team member owns a Safe with a signing passkey — a dedicated WebAuthn credential per fund (not the login passkey; user handle `sha256("la-caisse:safe-signer:<fundId>:<userId>")`, name "Signing key · <fund> · <email>") bound to a Safe passkey module v0.2.1 signer contract (`FundPasskeySigner`, owner kind `PASSKEY`) that the relayer deploys through `SafeWebAuthnSignerFactory`. The server holds no member key: a passkey owner's proposal is stored unsigned (`awaitingSignature`), the browser signs the `safeTxHash` as the WebAuthn challenge, the server verifies the assertion (`passkey-webauthn.ts`), asks the owner contract by EIP-1271 `eth_call`, stores a standalone contract signature (`passkey-signature.ts contractSignature`; `packSignatures` mixes them with ECDSA ones) and mints the step-up proof from that same ceremony. `FundSigner` (server-held keys) is legacy: `getOrCreateFundSigner` is gone, a stored key only signs on Safes that still list it as a `MEMBER` owner, every such Safe shows the "Move to passkeys" banner (`migration.ts`, `swapOwner` proposals signed by the other owners) and `retireServerKeys` erases the ciphertext once no unarchived Safe lists the address. Recovery rules (`owner-rules.ts`): with any team owner, owners ≥ threshold + 1 and threshold > one person's keys — the smallest passkey Safe is 2-of-3; an existing Safe may only change if the result is no further from the rules than today (`checkOwnerChange`), so a legacy 1-of-1 can still migrate. Mirror (tx-service) failures are kept on the row as `tx_service: …`.
- **Step-up before Safe money moves** (`services/auth/step-up.ts`): `hasRecentAuth(maxAgeMs)` is true only with a valid proof cookie (`services/auth/recent-auth.ts`, HMAC with the auth secret) bound to the user id, the hash of the session token and the request host, issued within 10 min. Proofs are minted only by `reauthWithPasswordAction` (`services/auth/step-up-actions.ts`, password verified against the credential account, no new session) and by the `hooks.after` on `/passkey/verify-authentication` in `better-auth.ts` (the passkey ceremony makes a new session on the host; the hook binds the proof to it). The Safe propose/sign/reject/retry actions and the manual mint/burn on `/token` (`manualMintDirectAction` / `manualBurnDirectAction`) answer `{ error, code: "reauth_required" }` without one (`services/auth/step-up-types.ts` holds the code and `isReauthRequired`); `components/reauth-dialog.tsx` (`useStepUp`) opens the re-auth dialog and retries the same submit. The page loads `userHasPasskey` (`services/auth/passkeys.ts`) server-side so the dialog knows whether to offer the passkey. Wire new sensitive actions the same way: gate after the role and input checks, before anything is written.

### Member login (card holders, plan "Bread card-holder voting")
- A card holder gets ONE login for life — a Better Auth `User` (email + password, passkeys) — linked to one `Member` per fund through `Member.userId`. Members are NOT staff: no `FundMember` row, so `requireFundRole` and the whole `(fund)` dashboard refuse a member session (`services/auth/dal.member.test.ts`). Member pages gate with `requireMember()` / `getCurrentMember()` in `services/auth/dal.ts`, which also 404 unless the fund opted in (`Fund.memberLoginEnabled`, Settings → Onboarding). Off = today's app exactly: no member pages, no links, every card public.
- **Pages** (`app/(fund-member)/member/*`): `/login`, `/signup`, `/forgot`, `/reset`, `/account` on the FUND host. Next refuses two route groups resolving to one URL and these paths exist for other hosts, so the pages live under `/member/*` and `proxy.ts` rewrites the short paths there for opted-in fund hosts only (the browser keeps the short URL). A fund on its own `<sub>.<apex>` host runs login and the passkey ceremony itself (rpID = apex); a custom-domain fund's `/login` hands members to the auth host (`?fund=<domain>`) and gets the session back through `/auth/exchange`, which needs no `FundMember`. No card pages: cards, PIN and votes live in the wallet.
- **Sign-up** (`services/member/auth.ts::signUpMember`, action `services/member/auth-actions.ts`): the `/join` form plus a password (`SignupForm withPassword`; the shared validation is `services/member/signup-core.ts`, the shared data loader `signup-form-data.ts`). Writes the `User` and its `credential` `Account` (hash from `auth.$context.password`) through Prisma in the SAME transaction as the `Member` — Better Auth's own sign-up stays disabled (`disableSignUp`, review S5) and the invite path untouched. A Member that already exists with that email is linked ONLY when the verification link is clicked: `EmailVerification.userId` binds the token to that exact User, and `consumeVerificationToken` sets `Member.userId`, `Member.emailVerifiedAt` and `User.emailVerified` together (never "whichever User has that email"). An email that already has a User is refused (sign in instead; a second fund is W-2). Per-IP `AttemptLimiter`s on the public actions.
- **Attachment** (`services/card/holder-sync.ts`): a card is attached at Citizen Pay — private on the wallet, can vote — iff `Member.userId` is set, `Member.emailVerifiedAt` is set and the fund has member login on: `PUT /v2/treasury/cards/{serial}/holder {holder_ref: User.id}`, else `DELETE`. Recomputed from the rows (idempotent), deferred with `after()` (`scheduleCardHolderSync` / `scheduleMemberCardHolderSync`) on every transition: activation, addCard, unassign, verification click, "remove my login". A 404 = the api route is not deployed: logged once, `Card.holderSyncedAt` stays null, `scripts/sync-card-holders.ts` replays. Enrolled copies (`enrolledFromRequest`) are never attached — only the issuer's key may.
- **Wallet OAuth client** (`services/auth/oauth-provider-config.ts`, `services/member/wallet-client.ts`): `citizenpay-wallet`, static confidential (`client_secret_basic`, secret from `WALLET_OAUTH_CLIENT_SECRET` hashed SHA-256/base64url like the plugin does), PKCE required, `skipConsent`, redirect URIs from `WALLET_OAUTH_REDIRECT_URIS` or the defaults; registered by the Better Auth before-hook on `/oauth2/authorize` + `/oauth2/token` (once per process) or `scripts/register-wallet-client.ts`. The api is an `OauthResource` (`CITIZENPAY_API_AUDIENCE`, `accessTokenTtl` 900): the wallet passes it as RFC 8707 `resource` and the access token's `aud` names it (an ARRAY once `openid` is in scope — the provider adds its userinfo endpoint; match on containment). Access tokens also carry `email` / `email_verified` (`customAccessTokenClaims`); `auth_time` is reserved on access tokens and lives in the ID token only (= the session's creation; a refresh keeps it; `prompt=login max_age=N` re-authenticates). Provider default refresh TTL is now 30 days (the wallet's); every `/api/mcp` resource pins `refreshTokenTtl` back to one day (migration + `ensureMcpResource`). The authorize query is passed through, so `fund=<treasury slug>` reaches `(auth-host)/login`, which brands itself (`services/member/fund-hint.ts`). `services/auth/wallet-oauth.test.ts` runs the whole flow on the real plugin with the memory adapter; `scripts/wallet-oauth-e2e.mjs` is the local wallet stand-in.

### MCP server (agents operating the dashboard)
- The app exposes an MCP endpoint at **`/api/mcp`** (Streamable HTTP, stateless JSON) so agents can operate the dashboard. It is mounted on every host, and a server is registered at the **fund's own URL** — `https://<fund-domain>/api/mcp` — so the host carries the fund the way it does for every page. Handler plumbing in `services/mcp/` (`handler.ts` builds a per-request `McpServer` from `@modelcontextprotocol/sdk`, resolving the host fund via `getCurrentFundDomain()`; `tools.ts` + `payout-tools.ts` register the toolset; `tool-kit.ts` holds the shared result/guard helpers).
- **Auth is OAuth 2.1 via `@better-auth/mcp`** (the OAuth-provider plugin preset, with the core `jwt()` plugin it requires — both registered in `services/auth/better-auth.ts`, `disabledPaths: ["/token"]` so the only token door is `/api/auth/oauth2/token`): open dynamic client registration (`/api/auth/oauth2/register`, PKCE mandatory for registered clients), access tokens are **JWTs** signed with the `Jwks` key (served at `/api/auth/jwks`) and audience-bound to a **resource**, refresh tokens are opaque `OauthRefreshToken` rows. Deliberately short-lived: access 1 h, refresh 24 h (the "short session"; a refresh token only exists when the client asked for `offline_access`, which our protected-resource metadata advertises). Plugin-owned tables: `OauthClient`, `OauthResource`, `OauthClientResource`, `OauthRefreshToken`, `OauthAccessToken`, `OauthConsent`, `OauthClientAssertion`, `Jwks` — same don't-rename rule as the other Better Auth tables, and better-auth ≥ 1.7.3 validates every column against the Prisma datamodel at startup (a mismatch rejects auth requests), so regenerate with `npx @better-auth/cli generate` when bumping.
- **One resource per host.** The RFC 8707 resource identifier (= the JWT `aud`) is the MCP URL the agent connects to: `https://<fund-domain>/api/mcp`, or the apex's. The plugin takes a single static `resource` (the apex, seeded into `OauthResource` at boot) and its `requireMcpAuth` verifies against that one URL, so we don't use it: `services/mcp/auth.ts::requireMcpAuthForHost` composes the same public pieces (`verifyAccessTokenRequest` + `createResourceServerChallenge`) around a resource resolved from the proxy-validated host (`getFundUrl` / `getApexUrl`, never the raw Host). A requested resource must exist as an `OauthResource` row or authorize fails with `invalid_target` (and dynamic registration fails while the apex row is missing): the migration backfills the apex and every fund, fund creation registers the new host (`registerFundMcpResource`), and the protected-resource metadata route re-creates a missing row on the way (`ensureMcpResource`, read-first, insert-only). Reserved subdomains (`www.`, …) and hosts the proxy can't classify have no MCP resource (404). `enforcePerClientResources` is off so any registered client may target any host. Expired refresh/access-token and client-assertion rows are swept by `app/api/cron/auth-exchange-cleanup`. The token's user is its `sub` claim; `client_credentials` tokens (sub = client) are refused by the handler.
- **Discovery**: root `/.well-known/oauth-protected-resource` (+ the path-inserted `/.well-known/oauth-protected-resource/api/mcp` the 401 challenge points at) are ours (`app/.well-known/`, per host, with CORS for browser clients); `/.well-known/oauth-authorization-server` and its path-inserted `/.well-known/oauth-authorization-server/api/auth` wrap the plugin's `oauthProviderAuthServerMetadata` (issuer = `https://auth.<APP_DOMAIN>/api/auth`); Better Auth itself answers `/api/auth/.well-known/*`. Endpoints live under `/api/auth/oauth2/*` (authorize, token, register, consent, userinfo, introspect, revoke).
- **Authorization UX**: an `authorize` hit without a session (or with `prompt=login`) redirects to the auth host's `/login?<signed authorize query>` (`sig`, `exp`, `ba_*` added by the plugin). The login page verifies it (`services/auth/oauth-resume.ts::readSignedOAuthQuery`, from the proxy's `x-search`) and the form hands it back: password sign-in passes it as `oauth_query` in the `signInEmail` body (`loginAction`), where the plugin finishes the authorize inside the sign-in call (it needs a `request` object — `oauthResumeCallContext` builds a synthetic one) and answers with the next hop — `{ redirect: true, url }`, possibly wrapped in a `Response`, or a thrown `APIError("FOUND")`; `oauthRedirectFrom` / `oauthRedirectFromError` cover all of them and the action returns it as `redirectTo` for the form to `window.location.assign` (a server-action `redirect()` is a soft navigation, which Cache Components can't do for the dynamic consent page); passkey sign-in re-enters `/api/auth/oauth2/authorize` with the original parameters (`services/auth/oauth-query.ts::authorizeResumeUrl`) once its cookie is set. The next hop is `/consent?<signed query>` (`app/(auth-host)/consent`, `consentAction` → `auth.api.oauth2Consent` with `oauth_query`) the first time a client asks, then the client's `redirect_uri` with the code. Mid-OAuth sign-ins never go through the cross-host exchange — the user stays on the auth host, whose session cookie is what the consent page needs. Swallowing the resume redirect as a credential error breaks the handshake.
- **Dev/e2e**: `scripts/mcp-oauth-e2e.mjs` drives the whole flow with the real MCP SDK client (discovery → registration → PKCE authorize → tool call → refresh) against a running dev server; it prints the authorize URL to open in a browser and listens for the callback itself.
- **Tenancy in tools**: `services/mcp/authz.ts::requireFundForTool(ctx, fundArg, minRole)` is the tenant gate, and every tool must go through it before touching fund data. It takes the fund from the request host (`x-fund-domain`, since servers are registered at a fund URL) and lets a call override it with an optional `fund` domain argument — the override is what makes one registration usable across the funds a user belongs to, and it's required on the apex, which belongs to no fund. Either way the check underneath (`requireFundAccessForUser`) is the same: resolve the canonical domain, then `FundMember` + role rank. Role floors mirror the pages (members OPERATOR+, token and payout tools ADMIN+). No tool may query by a raw fundId from input.
- **Payout tools** (`services/mcp/payout-tools.ts`) drive settlement end to end: drafts → create → reconcile issues → deduction → pay (returns the bank signing link) → burn. They call `services/payout/operations.ts`, the fund-parameterized engine the dashboard's server actions also call — never re-implement a money path in the MCP layer. Irreversible or token-moving tools take an explicit `confirm`.

### Domain language: "fund" / "caisse"
- The core unit is a **Fund** in code, **"caisse"** in French UI strings, **"fund"** in English UI strings. The Prisma model is `Fund`, the join model is `FundMember`, the per-fund role is `FundRole`. Service folder is `services/fund/`.
- **There is no "slug" concept** — `Fund.domain` stores the full canonical hostname (e.g. `acme.lacaisse.eu` for free funds, `funds.acme.com` for paid custom domains). One field, one identity.
- The create-fund form takes a "subdomain" input from the user (just the prefix, e.g. `acme`) and the server constructs `<subdomain>.<APP_DOMAIN>` before persisting. Custom-domain UX is TBD.

### Roles & multi-fund access
- **`User.globalRole`** (`USER` | `ADMIN`) — platform-level. `requireAdmin()` reads this. Set via SQL or an admin tool. Lives on our Prisma `User` row alongside the Better Auth columns.
- **`FundMember.role`** (`OWNER` > `ADMIN` > `OPERATOR` > `VIEWER`) — per-fund. Use `requireFundRole(minRole)` for any fund-scoped resource. Returns `{ user, fund, membership }`. The rank lives in `services/auth/roles.ts` (`FUND_ROLE_RANK` / `hasMinFundRole` / `isFundAdmin`) — a plain module so both the server DAL and client components can share it. `OPERATOR` is a restricted role that may **manage cards and members only**: card + member admin actions/pages are gated at `requireFundRole("OPERATOR")`, everything else stays `requireFundRole("ADMIN")` (which excludes OPERATOR by rank). Carve-out: `topUpCardAction` / `withdrawFromCardAction` (money on/off a card) stay ADMIN-only. The `(fund)` layout requires OPERATOR to enter; ADMIN-only pages self-guard and the sidebar hides links the role can't use.
- **No JIT sync, no second identity store**: Better Auth writes the `User` row itself at sign-up. There is no DB trigger, webhook, or upsert-on-read — one table is canonical for both identity and app-level data (role, name, memberships).
- `User.id` is a uuid generated by Postgres (`gen_random_uuid()`); the auth tables (`Session`, `Account`, `Passkey`) FK onto it with cascade delete.

### Fund routing (host = identity)
- Production: `<sub>.lacaisse.eu` (free) or any custom domain (paid). Dev: `<sub>.localhost:3000` (modern browsers resolve `*.localhost` to 127.0.0.1 — no `/etc/hosts` setup needed).
- `proxy.ts` classifies the host as `auth` (`auth.<APP_DOMAIN>`), `apex` (the apex itself or a reserved infra subdomain: `www`, `api`, `admin`, `app`), or `fund` — the latter via ONE lookup: `Fund.findUnique({ where: { domain: host } })`. There's no subdomain extraction; the host IS the fund identity. Auth/apex/reserved hosts short-circuit before the DB hit.
- proxy.ts always **strips inbound** `x-fund-domain` / `x-fund-id` / `x-host-type` / `x-pathname` / `x-search` so a client can't spoof the fund context or host classification. Sets `x-host-type` (and the fund headers on a match), plus `x-pathname` / `x-search` so DAL helpers can build a `return_to`.
- App code reads the fund via `services/fund/server.ts` (`getCurrentFund`, `getCurrentFundDomain`, `requireCurrentFund`, `getFundUrl`, `getApexUrl`) and the host kind via `services/host/server.ts` (`getHostType`, `getAuthUrl`). **Never re-parse the host.**
- `GET /api/internal/hostname-allowed?hostname=` (cron bearer) answers 200 only for a host this app serves (apex, auth host, a fund's `<sub>.<APP_DOMAIN>`, a registered custom `Fund.domain`), for the self-hosted platform's on-demand TLS; the rules are `services/host/hostname-allowed.ts`. The proxy passes `/api/health*`, `/api/internal/*` and `/api/maintenance/*` through without classifying the host (`services/host/platform-paths.ts`).
- `APP_DOMAIN` env var configures the apex (`localhost` in dev, `lacaisse.eu` in prod). `NEXT_PUBLIC_APP_DOMAIN` is the client-visible mirror (the create-fund form uses it for the suffix display).
- **Apex page logic**: `app/page.tsx` branches on `getHostType()`. Auth host → redirect (signed-in to apex, anonymous to `/login`). Fund host → redirect to `/dashboard` (the `(fund)` layout takes it from there). Apex → marketing landing for anonymous visitors, fund picker for signed-in users.
- **Cross-host redirects**: `redirect("/some-path")` stays on the current host. Use `redirect(getApexUrl("/some-path"))` when redirecting from a fund subdomain back to apex (e.g. `/account/*` pages).

### Forms (RHF + Zod + Server Actions)
- Pattern: client component uses `useForm` + `zodResolver`, calls a server action from inside `handleSubmit` via `useTransition`. Server action re-validates with the same Zod schema (don't trust the client). See `app/(auth-host)/login/login-form.tsx`.
- The server action returns `{ error: string } | { ok: true; ... }` on failure/info, or **doesn't return** (calls `redirect()`) on success.
- Schemas live in a non-`"use server"` file so they can be imported by both client and server.
- ⚠️ **`"use server"` files can only export async functions.** Exporting constants, types, schemas, or anything else gets silently transformed into a server-reference proxy. Build passes, runtime explodes the moment a client tries to use it (`X.map is not a function`, etc.). Co-locate non-action exports in a sibling `config.ts` / `schema.ts` and import from there.
- **Schema error messages are i18n keys** (e.g. `"auth.errors.passwordMin"`), not human strings. Forms call `tRoot(message as never, { min: ... } as never)` to resolve them. Server actions translate via `getTranslations()` before returning.

### Internationalization (next-intl)
- Cookie-based locale (no URL prefix). Default locale: **`fr`**.
- Messages live in `messages/fr.json` + `messages/en.json`. Add a new locale = add a JSON file + extend `SUPPORTED_LOCALES` in `services/i18n/locale.ts`.
- Server: `await getTranslations("namespace")`. Client: `useTranslations("namespace")`. Never call hooks inside JSX — assign at the top of the component.
- For dynamic key lookup (e.g. resolving a message that came from a Zod schema), get a "root" `t` via `useTranslations()` (no namespace) and pass `key as never` to bypass the strict key typing.
- Locale switcher: `components/locale-switcher.tsx`, embedded in the auth layout footer.

### Passkeys (WebAuthn)
- Handled entirely by the **`@better-auth/passkey` plugin** (registered in `services/auth/better-auth.ts`). The old self-implemented `@simplewebauthn` flow — `WebAuthnCredential` model, challenge cookies, magic-link session bridge — is gone; the plugin owns challenges, verification, and session creation.
- Credentials live in the **`Passkey`** Prisma model. Field shapes are fixed by the plugin — e.g. `transports` is a comma-separated string, not a Postgres array.
- **rpID** = `APP_DOMAIN` (the apex), so a passkey registered on `acme.lacaisse.eu` works on every fund subdomain and the apex. `origin` is left unset — the plugin accepts any request origin within rpID scope.
- Client API: `signIn.passkey()` for discoverable-credential login (see `app/(auth-host)/login/login-form.tsx`), `authClient.passkey.addPasskey()` / `deletePasskey()` for management. The ceremony POSTs to `/api/auth/passkey/*` on the **current origin** — if a host is missing from `trustedOrigins` in `better-auth.ts`, the ceremony fails with "Invalid origin".
- Post-signup nudge: fresh signups land on the apex with `?welcome=passkey`; `app/page.tsx` offers one-tap passkey setup when the user has none.

### Email (Resend, two layers)
- **Auth-flow emails are sent by us now** (no more Supabase SMTP hop). Better Auth callbacks in `services/auth/better-auth.ts` do the sending — `sendResetPassword` builds a localized message via `getTranslations("auth.emails.resetPassword")` and hands it to `services/email/resend.ts`. Email verification is currently **off** (`requireEmailVerification: false`); when product wants it, flip the flag and add a `sendVerificationEmail` callback in the same style.
- **Our direct transactional sends** (fund invites, welcome flow, anything we trigger from a server action) go through `services/email/resend.ts` (`sendEmail({ to, subject, text/html, replyTo })`). Uses `RESEND_API_KEY` + `EMAIL_FROM` from env. Throws on Resend errors so the caller decides whether to surface or log+continue.
- Don't reach for the Resend SDK directly from a route or action — always go through `services/email/`. Same swap-out story as the rest of the service modules.
- React Email isn't set up yet. When we need branded templates, install `@react-email/components` and add a `services/email/templates/` directory; render to HTML via `render()` and pass to `sendEmail({ html })`.

### Crypto / secrets at rest
- `services/crypto/secret.ts` is the **only** path to encrypt/decrypt secrets stored in Prisma rows. Don't roll a second AES helper. Envelope format is `v1:<iv‖tag‖ct>` base64, or `v2:` when the GCM tag also binds caller-supplied additional data (not stored — e.g. `signer:<fundId>:<userId>` for `FundSigner.privateKeyEnc`); versioning lets us rotate algorithms later.
- Key comes from `APP_CRED_KEY` (32 raw bytes / 64 hex). Missing / malformed key throws at first use — fail loudly, don't silently skip encryption. The same key is the HMAC key of unsubscribe links (`services/member/unsubscribe.ts`) and seals conversion tickets (`services/convert/engine.ts`).
- **Key rotation** is zero-downtime: `encryptSecret` always uses `APP_CRED_KEY`; `decryptSecret` (and `verifyUnsubscribeToken`) fall back to `APP_CRED_KEY_PREVIOUS` when set, with the v2 binding enforced on both. Recipe in `.env.example`: set both keys → deploy → `npx tsx scripts/rotate-app-cred-key.ts --apply` re-encrypts every `*Enc` cell in one transaction (dry run by default, refuses to write if any row opens with neither key) → dry run shows everything current → drop `APP_CRED_KEY_PREVIOUS` → deploy. The script carries its own copy of the cipher in `scripts/lib/app-cred-rotation.ts` (`server-only` keeps the service module out of tsx); its test cross-checks the copy against `services/crypto/secret.ts`, so a format change must update both. Add any new `*Enc` column to the script's column list. The scan and the conditioned write live in `scripts/lib/app-cred-rotation-db.ts`, shared with `POST /api/maintenance/reencrypt-app-cred` (`services/crypto/reencrypt.ts`, cron bearer, at most 50 cells per call, `{done, reencrypted, remaining}`), which the self-hosted platform calls instead of the script (docs/container.md).
- Encrypted columns conventionally end in `*Enc`. CLI helper: `node scripts/encrypt-secret.mjs <plaintext>` (or pipe stdin) emits the envelope ready to paste into SQL.

### CitizenPay treasury handoff (redirect)
- Two CP flows, both wired, sharing one callback. **Flow 1 — register a treasury**: a fund with no `citizenPayFundId` gets a "Register on Citizen Pay" button in settings; `/api/citizenpay/register` redirects to CP's `/v2/treasury/register` with prefill (`name` = `tokenName ?? name`, `symbol`, `decimals=6`, `chain` = Gnosis' `chain_prefix`, `"100"` in prod — must match exactly, the dashboard falls back to the virtual chain on an unknown prefix — overridable with `CITIZENPAY_REGISTER_CHAIN`); CP's dashboard creates the treasury, deploys the token if asked, mints the first key and comes back. The route refuses (`already_registered`) once a treasury id is set, and (`registration_pending`) while an attempt from the last 30 minutes is still open — the settings notice then offers `GET /api/citizenpay/register?resume=1` (same fund state, back to CP's form; `resumeTreasuryRegistration`) and a `POST /api/citizenpay/register` "start over" (`cancelPendingRegistration` expires the attempts, then the normal start; a stale CP tab fails at the callback with `state_expired`). **Flow 2 — mint a key for an existing treasury**: the admin pastes the `citizenPayFundId` into fund settings (the fallback form under the register button), then `/api/citizenpay/connect` redirects to `/v2/treasury/keys/register` to mint (or rotate) the matching API key.
- Service entry points: `services/citizenpay/connect.ts::initiateTreasuryRegistration` and `::initiateKeyIssue`; the prefill builder is the pure `services/citizenpay/register-prefill.ts` (unit-tested). The connect route picks "initial" vs "rotated" for the `key_name` (visible in CP's audit log) based on whether `citizenPayApiKeyId` is already set on the fund.
- **CSRF model**: CP generates its own opaque `state` server-side and we have no way to validate it on its own. We mint a *fund state* (random, 30-min TTL, single-use) into `CitizenPayConnectAttempt` and **encode it as a URL path segment** in the `redirect_uri` we hand to CP: `https://<fund>.lacaisse.eu/api/citizenpay/callback/<fundState>`. Path-segment (not query) because CP unconditionally appends `?state=…&pickup=…&treasury_id=…` and a query-encoded fund state would collide with a second `?`.
- **Allowlist** (CP-side, out of band): CP rejects any `redirect_uri` whose host isn't in their `TREASURY_REGISTER_ALLOWED_DOMAINS`. We need `*.lacaisse.eu` registered for prod and `localhost` for dev. If CP returns an "allowlist" error in step 1, ask CP ops to add the host before debugging anything on our side.
- The callback at `app/api/citizenpay/callback/[fundState]/route.ts` is intentionally **public** (the user is mid-redirect; the fund host's session cookie may not have survived the round-trip). Auth is the fund-state row + CP's pickup token — hitting it without a valid fund state can't do anything.
- Cleanup: `app/api/cron/auth-exchange-cleanup` sweeps expired `CitizenPayConnectAttempt` rows on the same schedule as `AuthExchange`.

### CitizenPay (Treasury API v2)
- Live client lives at `services/citizenpay/live-client.ts`; the low-level OpenAPI-faithful wrapper is `services/citizenpay/api.ts` (one method per endpoint, integer-cents on the wire). Use `getCitizenPayClient(fund)` — never instantiate either directly.
- **Per-fund credentials**, not platform-wide. Each `Fund` carries `citizenPayApiKeyId` (plaintext eth address) and `citizenPayApiKeyEnc` (AES-256-GCM encrypted via `APP_CRED_KEY` — see `services/crypto/secret.ts`). The factory takes the fund subset so every call site is type-checked to load these columns.
- **Mock vs live is chosen by `CITIZENPAY_API_BASE_URL`** alone. Unset → in-process mock for everything (dev). Set → live mode and any fund missing creds **throws immediately** (no silent mock fallback). Match the env to the deployment.
- **Token mint/burn does NOT go through this client.** Token ops use the CitizenPay bundler (`CITIZENPAY_BUNDLER_URL`) via `services/token/*` (TBD) — paymaster signature + UserOp submission. Don't add new mint methods to `CitizenPayClient`.
- **`submitMint` takes a wallet address (`toAccount`) but the v2 endpoint identifies the card by serial.** The live client looks up `Card.serialNumber` via Prisma, scoped to the client's fund (`getCitizenPayClient` passes `fund.id`; `Card.serialNumber` / `Card.account` are unique **per fund**, since a card can be enrolled in several funds — see `services/card/enrollment-requests.ts`). All call sites already pass the account — no change needed. This path will be removed once the token-service mint flow is wired.
- **`getOperationStatus` has no v2 equivalent** — top-up / charge / withdraw are synchronous and return the on-chain `txHash` directly. The live impl always returns CONFIRMED, so the polling cron flips ops on its first tick. Don't add fake intermediate states.
- **`listBankTransactions` is implemented and live** — CP shipped the bank-transfer endpoints (api commit `feat(treasury): bank-connection status/balance/transactions`). The live impl pages the banking feed newest-first, stopping at the `since` watermark (full history on first sync, capped at `MAX_PAGES`); ingest upserts are idempotent on `(fundId, externalId)`. The bank-sync cron and the "add order from a bank transfer" picker both read this real data.
- **Treasury top-up URL** (the public card wallet's "Add funds" button): `services/citizenpay/top-up-url.ts::topUpUrlFor` (pure) gives `<getFundUrl(domain)>/pay/{serial}` (the cotisation page) only for `FIXED_PERIOD`; the literal `{serial}` is expanded by the wallet. `PAY_AND_GO` is null: Citizen Pay serves its own checkout as the treasury's default `top_up_url` (CP api `GET /v2/treasuries` falls back to `https://checkout.citizenpay.xyz/top-up/<treasury slug>?serial={serial}` for a treasury row with none, once the issuer has a `topup_place`), so La Caisse publishes nothing and clears the `/pay/{serial}` link it published before. `DISABLED` is null too (no money from members). **A null never means "clear whatever is there"**: the sync reads the treasury's current `top_up_url` (`getTreasuryTopUpUrl`, `GET /v2/treasury`) and clears only a link La Caisse published itself (`isOwnTopUpUrl` — the fund's own `/pay/{serial}`); any other value, e.g. Brussels Pay's CP checkout (`https://checkout.citizenpay.xyz/topup` on treasury `bxl`, fund `paybrussels.lacaisse.eu`), is left alone (`foreign_url`, logged), and a failed read clears nothing. `sync-top-up-url.ts::syncTreasuryTopUpUrl` pushes it (`PATCH /v2/treasury { topUpUrl }`, 3 s timeout), best-effort, and never sends a non-https link to the live API. Request paths call `scheduleTreasuryTopUpUrlSync` (Next `after()`, off the response path) — the general settings save and `consumeConnect` do; anything else that changes `Fund.domain` or `allocationMode` must too. `scripts/sync-top-up-urls.ts` backfills every connected fund (dry run by default, `--apply` writes, refuses non-https URLs, same own-link-only clear rule — the dry run prints `(leave: CP-managed URL)` for such a fund).
- **Treasury kind** (api#260, `treasuries.kind`, the api's docs/card-freeze.md "Fund vs token"): the api creates every treasury as a plain `token` (a currency places may accept — Monerium EURe, business tokens) and the Citizen Wallet lists only `fund`s (`GET /v2/treasuries?kind=fund`); only La Caisse knows which treasuries are its caisses, so **La Caisse marks its own**: `services/citizenpay/sync-fund-kind.ts::syncTreasuryKind` sends `PATCH /v2/treasury { kind: "fund" }` (`setTreasuryKind`, 3 s timeout), best-effort, never `token`, no environment guard (nothing in the body depends on the host). `scheduleTreasuryKindSync` (Next `after()`) runs from `consumeConnect` (both flows) and the general settings save, next to the top-up URL sync — so a re-save repairs a treasury the api still holds as a token. The api's migration 175 marked the four funds connected on 2026-11-06 (bxl, de-token, class, zinne); `scripts/sync-fund-kind.ts [--dry|--apply]` replays it for every connected fund (dry run by default; reads each treasury's slug + kind when `APP_CRED_KEY` + `CITIZENPAY_API_BASE_URL` are set and writes only the ones not already a fund). An api that predates the field answers 400 (none of the fields it knows is present): logged, nothing fails, the script catches up once it is deployed.
- **Admin charge-on-card towards a merchant** (`/cards/<id>` → "Charge at a merchant"): collects a sale a merchant's pay-pos failed to take from the member's card, through CP's treasury-key charge-card routes (`listOpenPlaceOrders` / `chargeCardForOrder` / `chargeCardOnPlace` on the client; api `places.openOrders`, `places.chargeCard`, `orders.chargeCard`). Server actions in `services/card/charge-actions.ts` (ADMIN-only, like top-up). The PIN is hashed in the browser (`services/card/pin-hash.ts`, the pay-pos digest — never bump its version alone) and only the digest travels; a manual charge carries an idempotency key minted per opened dialog so a retry reuses the order CP created. `POST /v2/treasury/cards/{serial}/charge` (`api.ts cards.charge`) moves tokens but records no order — don't use it for sales. The dev mock refuses by serial suffix (`…PIN`, `…BAD`, `…POOR`, `…BLOCKED`, `…LOST`).
- **PIN block (D12, api PR P)**: Citizen Pay blocks a card after three wrong PIN entries (`pin_blocked_at` on the api) and that block is the api's, a fund block (lost card) is La Caisse's. `Card.blockedReason` (`PIN` / `FUND`, null = ACTIVE/INACTIVE or a legacy block, read as FUND) tells them apart; the one pure rule is `services/card/pin-block-rules.ts::planCardStateSync`, applied by `services/card/pin-block.ts` (local row + `CardEvent` audit line). The card sync's run step (`pushOneCardStatusAction` re-reads each card; the preview writes nothing) imports a PIN block the api reports instead of pushing ACTIVE over it, pulls a local PIN block the api no longer reports back to the api's status (holder set a new PIN in the wallet), and still pushes fund blocks — a fund block even supersedes a PIN block, as on the api. `setCardStatus` no longer swallows 409s: the api's 409 on a plain `active` for a PIN-blocked card means "import, don't push" (`pushOneCardStatusAction`, `setCardStatusAction`). The status dialog refuses PIN-blocked cards; the way out is the explicit unblock on the card page (`services/card/pin-block-actions.ts`, ADMIN + step-up, `PATCH {status:"active", unblock:true}`, audit line with the actor). **Events webhook**: the api posts `card.blocked` / `card.unblocked` to `POST /api/citizenpay/events` on the fund's host (the fund is the host's `x-fund-id`; the payload's `project` is only cross-checked, and everything before the signature check is one generic 401), signed `X-CitizenPay-Signature = HMAC-SHA256(secret, X-CitizenPay-Timestamp + "." + body)` (`events-signature.ts`: constant-time compare, 5-minute skew); every delivery is written to `CitizenPayEvent` by event id first (idempotent; a `FAILED` one is retried) and **the payload is never applied** — the handler (`services/citizenpay/events.ts`) re-reads `GET /v2/treasury/cards/{serial}` and applies that. A confirmed block sends `CARD_PIN_BLOCKED` to the fund's OWNER/ADMIN and `CARD_PIN_BLOCKED_HOLDER` to the bound member (`services/card/pin-block-emails.ts`, Email rows keyed on the event id, linked to the card). The webhook url + secret (`Fund.citizenPayEventsSecretEnc`, encrypted like the api key and stored before it is sent) are registered through `PATCH /v2/treasury { eventsWebhookUrl, eventsWebhookSecret }` by `events-webhook.ts` — from `consumeConnect` (after the redirect) and the Settings → Citizen Pay button, which also shows the last delivery; never a non-https url against the live api. Deploy this before the api's PR P: without it PR P's 409 makes the sync error on PIN-blocked cards.
- The spec also exposes Places, Payouts, bulk-card ops, and payment-request flows — they're all available via `api.ts` but not yet bolted onto the high-level interface. Add new methods to `CitizenPayClient` only when a call site actually needs them.
- **Open-banking card top-up (PAY_AND_GO)**: `/pay/<serial>` (no longer the wallet's "Add funds" link for PAY_AND_GO — that is CP's checkout now, see "Treasury top-up URL"; still reachable from the reminder email or directly) sends the member through CP's treasury sign door (`topUpSignUrl` → `GET /v2/treasury/{id}/payments/request/sign?topUpAmount=&accountAddress=`), which creates the Ponto request (remittance `cp-<paymentRequestId>`) and redirects to the bank in one GET; CP appends `paymentRequestId` to our `redirectUri` on the way back. **CP does not mint for these** — `services/card-topup/settle.ts` does, 1:1, once `getPaymentRequest` says signed, guarded so it mints once (`CardTopUp.tokenOperationId` claim). The POST `payments/request` door is NOT used: it goes through Ponto Connect with the token address as account id, which CP's own payment cron (Ponto Hub) can't see. Safety nets: the bank-sync cron sweeps open top-ups (and finishes / flags half-done mints), and ingest recognises `cp-<id>` deposits before member matching (`matchMethod` `CARD_TOPUP`, no tier mint, no period); a `cp-<id>` deposit it can't take as is (amount differs, second deposit, treasury unverified) is **held** unmatched with a note, never sent on to member matching. Rules that keep it from minting twice: `retryPendingMints` skips ops linked to a `CardTopUp` (`cardTopUp: { is: null }`) — the top-up flow owns its retries; once `mintToken` resolves, bookkeeping failures are logged, never turned into FAILED / a released claim. **Treasury check**: a request only counts when CP's status read returns `treasuryId` = `Fund.citizenPayFundId` (CP api#224); before that ships, nothing mints from CP's status. A PAY_AND_GO fund that isn't `isTopUpReady` gets the old transfer page (IBAN + EPC QR) on `/pay/<serial>`.

### Fund setup checklist & subscription
- A fund walks three self-service steps before it runs on La Caisse: **register on Citizen Pay** (treasury id + API key, the flows above) → **activate open banking** on the CP dashboard (the bank connection belongs to the treasury's business; status from `GET /v2/treasury/banking/status`, link built from `Fund.citizenPayBusinessId`, written on connect and backfilled lazily by `services/citizenpay/business-id.ts::resolveCitizenPayBusinessId`) → **accept the hosting subscription**. Statuses are derived by the pure `services/fund-setup/steps.ts`; the rules are in its header.
- Connecting is also when La Caisse tells Citizen Pay the treasury is a **fund** (`kind: "fund"`, what the Citizen Wallet lists; see "Treasury kind" under CitizenPay) — `consumeConnect` schedules it with the top-up URL and the events webhook, the General settings save repeats it, and `scripts/sync-fund-kind.ts` backfills funds connected before this existed.
- Code lives in `services/fund-setup/*` (`steps.ts`, `citizenpay-dashboard.ts` for the CP dashboard links, `schema.ts`, `admin-actions.ts`, `emails.ts`); the checklist renders on the dashboard, the acceptance on **Settings → Subscription**.
- The subscription (€`SUBSCRIPTION_MONTHLY_EUR`/month, `config.ts`) is **OWNER-only** — `acceptSubscriptionAction` gates at `requireFundRole("OWNER")`; other admins see the plan and an owner-only note. It is recorded on `Fund.subscriptionAcceptedAt` / `subscriptionAcceptedByUserId` + the `billing*` columns with a conditional `updateMany` (`subscriptionAcceptedAt: null`), so a double submit writes and emails once. The app never clears it.
- Billing itself runs on **Citizen Pay's side**: after the write, `after()` sends a localised confirmation to the billing email and a plain-English notice to `PLATFORM_BILLING_EMAIL` (skipped with a log when unset) so CP ops open the billing account. Both are best-effort and never fail the acceptance. Invoices are read on the CP dashboard (`.../<businessId>/billing`).
- **Free hosting (waiver)**: `Fund.subscriptionWaivedAt` + `subscriptionWaiverReason` (+ optional `subscriptionWaiverCodeId`) settle the step without an acceptance (`steps.ts::isSubscriptionSettled` = accepted OR waived). Two doors: a **waiver code** — `SubscriptionWaiverCode` (12 chars Crockford base32, `waiver-codes.ts` normalises/formats, `maxUses`/`expiresAt`/`revokedAt`), minted by a platform admin (`User.globalRole ADMIN`) on the apex at `/admin/waivers` (`waiver-admin-actions.ts`, linked from the fund picker) and redeemed by an OWNER on Settings → Subscription ("Have an invite code?", `admin-actions.ts::redeemWaiverCodeAction`: one transaction, conditional claim of a use + conditional fund write, rolled back if the fund settled meanwhile; the code's `label` becomes the fund's reason) — or the shell, `scripts/waive-subscription.ts <domain> --reason "…" --apply` (`--all … --apply --confirm` for every unsettled fund: the grandfathering tool at deploy). A waived fund never accepts (`acceptSubscriptionAction` refuses) and nothing in the app clears a waiver; revoking a code closes it for new redemptions only.
- **`/join` — "Start your fund"** (apex, public): anyone creates their account and their fund in one go; the fund starts unsettled, like one opened from `/new`, and the dashboard's checklist asks for the subscription. An invite code is the one extra ("I have an invite code" inside the form, or a shared link `/join?code=`): a usable waiver code waives the subscription from the start, without anyone creating the fund and inviting the holder first. The code is handled like the staff-invite token: checked without being consumed when the page opens with `?code=` or when the field is left (`join-actions.ts::checkJoinCodeAction`, the same `lookupJoinCode`), claimed inside the transaction that creates account and fund. Rules in `services/fund-setup/join.ts`: ONE answer for every unusable code — unknown, revoked, expired and used up all read "not valid" (`waiver-claim.ts::findUsableWaiverCode` returns null for each; the page never confirms a guessed code exists); the code travels in URLs by design (`/join?code=`, `/new?code=`, the login's `return_to`), so those pages export `metadata.referrer: "no-referrer"`; in-memory `AttemptLimiter`s like the member login's — per IP on checks that fail (`lookupJoinCode`) and on submits that end (`countJoinSubmit`: refused for the code, created, or answered by email — a "subdomain taken" spends nothing), per code on every submit that carries one (`allowJoinSubmit`), per address on the existing-account email. The submit is `join-actions.ts::joinAction`: one `$transaction` — with a code, `claimWaiverCodeUse` first (the conditional `updateMany` the redeem action also uses) — then the `User` + credential `Account` the member sign-up writes (hash from `auth.$context.password`, `emailVerified: false` — nothing proved the inbox), then the fund through `services/fund/create.ts::createFundRecord` with the person as OWNER and, with a code, `subscriptionWaivedAt`/`subscriptionWaiverReason`/`subscriptionWaiverCodeId` and `createdWithWaiverCodeId` (what `/admin/waivers` shows as "created with this code" vs "redeemed it"). No "does this address exist" read: the races are answered from the writes — the claim finding nothing (same words as a wrong code), the email's unique (the answer goes BY EMAIL to that inbox, `join-emails.ts`, with the sign-in link coming back to `/new`, `?code=` along when there was one; the screen only says an email went out, so the form cannot enumerate accounts), the domain's unique (subdomain taken). Then Better Auth's verification email (`emailVerification.sendVerificationEmail` in `better-auth.ts`, 24 h link to `/api/auth/verify-email` on the auth host, callback = the fund dashboard; the dashboard shows an "unverified" notice with a resend — `services/auth/verification-actions.ts`, 3/hour per account — until the link is opened; `requireEmailVerification` stays off), sign-in on the apex (best-effort) and the cross-host exchange to the fund's `/dashboard`. The page is `app/(apex)/start`: `/join` is the member sign-up's path on fund hosts and Next refuses two route groups resolving to one URL, so `proxy.ts` rewrites the apex `/join` to `/start` (every method — the actions POST to the public path) and the page 308s a direct `/start` visit (`x-pathname`) back to `/join`, so one public URL exists. A signed-in visitor goes to `/new` (the code along, as typed): **any signed-in account may open a fund there** — the door is as open as `/join`'s, and a card holder's member login becomes OWNER of the new fund only, never staff of the fund it holds a card at; `/new` shows a code that stopped being usable as "not valid" over the plain form, and `createFundAction` claims a usable one and creates the fund waived in one transaction.

### Token (Gnosis by default)
- Mint + burn run from this repo. We do not call CitizenPay's REST API for token ops — UserOps go through the CitizenPay bundler (`CITIZENPAY_BUNDLER_URL`, paymaster-signature + UserOp-submission endpoints, docs TBD).
- Read-side (balances, transfer history, on-chain `hasRole` check) goes via Alchemy on Gnosis: `ALCHEMY_API_KEY` for RPC + Token API + Transfers API. Alchemy AA / paymaster is **not** used — Alchemy doesn't support gas sponsorship on Gnosis.
- **Token identity comes from the connected CP treasury, not from admin input.** `Fund.tokenAddress`, `tokenChainId`, `tokenDecimals`, `tokenName`, `tokenSymbol` are caches written by `services/citizenpay/sync.ts::fetchTokenInfo`, which is invoked from `consumeConnect` immediately after a successful pickup. The settings Token tab is **read-only**. To refresh, re-issue the API key from the CitizenPay tab.
- The `treasury.get()` call in `services/citizenpay/api.ts` is a **guessed** shape against `GET /v2/treasury` — when CP confirms the endpoint, update the path + `TreasuryWire` shape + the normaliser in `sync.ts`. Both flat (`token_address`, `chain`, …) and nested (`token: { address, chain, … }`) shapes are accepted today.
- **Minting + burning are implemented and live.** The minter wallet fields on `Fund` (`tokenMinterPrivateKeyEnc`, `tokenMinterEoaAddress`, `tokenMinterSmartAccountAddress`, `tokenMintEnabledAt`) are populated and used — `mintToken` / `burnFromToken` in `services/token/userop.ts` build the safe-mint/burn calldata and submit a paymaster-sponsored UserOp through the CitizenPay bundler (`CITIZENPAY_BUNDLER_URL`). `loadFundContext` requires the three minter fields to be set and fails loudly otherwise.
- The smart-account `sender` address **is** derived counterfactually — `services/token/smart-account.ts::deriveSmartAccountAddress` calls the CP Safe Account factory's `getAddress(owner, nonce)` with **salt nonce 0** (one minter EOA → one Safe per fund), using the factory cached on `Fund.citizenPayAccountFactoryAddress`. CREATE2 → the address is identical on every supported chain; we RPC against Gnosis.
- **Operator-facing manual mint/burn lives on the `/token` page**, backed by `services/token-operations/admin-actions.ts` (`manualMintDirectAction` / `manualBurnDirectAction`): ADMIN role, a required note, and a step-up re-authentication (see Auth). Internal flows — fund account moves (`services/token-account/admin-actions.ts`), the payout reconcile flow (`fixOrderAction`, the auto-mint on manual order creation) — call the fund-parameterized core `mintDirect` / `burnDirect` (`services/token-operations/direct.ts`) directly with their own audit trigger, so neither the note nor the step-up applies to them. Each op is recorded as a `TokenOperation` row (`PENDING` → `CONFIRMED`/`FAILED`).

### shadcn base-nova vs Radix shadcn
- **No `asChild` prop on Button** (and other primitives). To style a `<Link>` like a button, use the exported `buttonVariants({ variant })` as a className. For dialog triggers and similar, Base UI primitives accept a **`render` prop** (e.g. `<DialogTrigger render={<Button>...</Button>} />`).
- The `form` component (Form/FormField/FormItem/FormLabel/FormMessage) **does not exist** in base-nova. Compose RHF directly with `Input`/`Label`/`Alert` — see the auth forms for the canonical pattern.
